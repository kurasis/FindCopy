# End-user security audit — 2026-10-07

The initial source was `330ffd07cbcc956037c14510564126ac44118007`, with a clean
working tree. This audit covers application/Core source, resolved dependencies,
the manifest, SDK installation, build/test helpers, and release workflows.
Static inspection preceded execution. Dynamic checks used this isolated cloud
Linux workspace and disposable data under `/tmp/findcopy-security`; no installer,
privileged Windows helper, or destructive test ran on an end user's computer.

## Confirmed findings and fixes

### S-01: unsigned directory-record offset can escape a native buffer

- **Location:** `src/FindCopy.Core/WindowsFileSystem.cs`, former
  `BatchLooksValid`, particularly `off + 88` and `off += next` before pointer
  dereferences. The caller is now `EnumerateExtd`, line 110; the replacement is
  `src/FindCopy.Core/DirectoryBatchValidator.cs:10–25`.
- **Condition and impact:** a malformed `FILE_ID_EXTD_DIR_INFO` chain can set
  `NextEntryOffset` to `0xfffffff8`. The old unsigned addition wraps the header
  check to 80, then dereferences a pointer almost 4 GiB beyond the allocation.
  A process crash/out-of-bounds read is possible. Remote control over a Windows
  native filesystem response, or code execution from this read, was **not**
  demonstrated; normal NTFS filenames alone do not provide this control.
- **Risk:** **medium, conditional**. This is a confirmed memory-safety defect
  in validation of external native data, with a substantial exploitation
  prerequisite. It is not evidence of an ordinary-file remote exploit.
- **Minimal fix applied:** validate with bounded managed spans, constrain each
  unsigned offset to the remaining buffer before conversion/addition, and require
  the next complete header before native decoding. Public interfaces are unchanged.
- **Evidence:** S1–S3 accept valid Unicode/multiple records and reject wrapping,
  out-of-buffer, overlapping/unaligned offsets and truncated/invalid lengths.
  The dangerous old pointer dereference was not executed.

### S-02: dense benchmark cleanup can permanently delete an added document

- **Location:** `tools/FindCopy.Bench/ExtendedAcceptance.cs`, `Dense`, former
  `Directory.Delete(root, recursive: true)`; current lines 100–148.
- **Condition and impact:** a file added to `dense-D` after the final scan but
  before cleanup is recursively deleted, although it was never generated by the
  benchmark. An extra file already present during a scan normally fails the file
  count gate; the vulnerable window is specifically after the final measurement.
  This affects the optional developer acceptance tool, not desktop deletion.
- **Risk:** **medium**: irreversible loss of unrelated data within the chosen
  acceptance workspace; requires using the tool and a late file addition.
- **Minimal fix applied, with user approval:** reject unexpected entries and
  linked dataset directories/files/markers before generation, mutation and
  cleanup. Delete only `d0.bin`/`d1.bin`, then remove the directory nonrecursively.
  An unrelated late entry causes failure and is preserved.
- **Evidence:** a separate harness intercepted the old runner's final measurement
  output and added a test document. Old runner: exit 0, document deleted. S7 uses
  the same insertion point and verifies failure with the document preserved.
  S4–S6 cover an existing added document, normal completion, and a directory
  symlink/junction with an untouched target. Fixtures contained no real user data.

### S-03: extension-based opening warning does not cover all executable associations

- **Location:** `src/FindCopy.App/MainWindow.xaml.cs`, former
  `RunnableExtensions` and `OnOpenFile`; current lines 575–591.
- **Condition and impact:** the user chooses **Open** on a found file whose
  extension has an executable Windows association but is absent from the list,
  including a custom association. `UseShellExecute = true` then starts its handler
  without the program/script confirmation. Windows association handlers may run
  code with the current user's access to documents and other data. A user action
  is required; scanning itself does not start discovered files.
- **Risk:** **medium**, involving user interaction and an unsafe association or
  active file. This is a warning-policy bypass, not demonstrated shell injection.
- **Minimal fix applied, with user approval:** require an explicit confirmation
  for every file association, with **No** as the dialog default. The displayed
  path is exactly the path passed to Windows, without assembled command arguments.
- **Evidence:** the WPF test exercises denied/approved opening for ordinary,
  executable, console and unknown extensions using an injected launch callback.
  It must never launch a process after refusal and must preserve association
  behavior after approval. Real potentially malicious files are never launched.

### S-04: benchmark generation follows a marker link outside its dataset

- **Location:** `tools/FindCopy.Bench/DatasetGenerator.cs:15–21`, `Generate`, and
  line 77, `File.WriteAllText(marker, version)`; `Dense` calls that generator.
- **Condition and impact:** an otherwise recognized acceptance workspace contains
  a `dense-D.generated` file symlink and a fresh/empty dataset directory. Generation
  follows that link and creates or overwrites its target with marker text, even
  outside the dataset. This requires control of the optional tool's workspace,
  or an accidental preexisting link; it does not provide privilege elevation or
  affect the desktop application directly.
- **Risk:** **medium**, owing to possible corruption of an unrelated accessible
  file; limited to developer acceptance workspaces.
- **Minimal fix applied, within the approved benchmark safety change:** inspect
  the marker's `LinkTarget` and reparse attributes before generation. This does not
  depend on platform-specific `File.Exists` behavior for dangling links.
- **Evidence:** the original runner exited 0 while creating an external test file
  through a dangling marker in the isolated reproduction. S8 rejects both missing
  and existing targets and verifies no creation/overwrite occurs.

## What was checked

- **Processes:** application calls are explicit Explorer reveal and file opening.
  Explorer uses the Windows directory's `explorer.exe` with `UseShellExecute = false`.
  No application `cmd`/PowerShell shell, remote code downloader or user-input shell
  concatenation was found. CI-only helpers start reviewed build/test tools; the
  junction test's `cmd /c mklink` uses disposable generated test paths.
- **Files:** deletion freshly compares bytes to a retained keeper, checks opened
  identities/snapshots and removes permanent Windows candidates by handle.
  Name-surrogate file links are rejected. Recovery validates recorded identities,
  personal Recycle Bin metadata and local paths, locks destination ancestors and
  refuses replacement of an existing destination. Journal JSON is bounded and
  atomically saved. Cached inventory rejects traversal components/separators and
  validates its checksum/metadata. The checksum is not a keyed authenticity proof
  against somebody who already can modify the user's cache. CSV escaping covers
  quoted absolute paths; no attacker-controlled formula-leading path was proven.
- **Archives/install:** the application has no archive extractor or installer;
  distribution is a self-contained EXE. SDK setup downloads pinned Microsoft
  archives over HTTPS and checks an independently pinned SHA-512 before extraction
  and execution. It does not extract arbitrary user-provided archives. Native
  libraries in single-file publishing are extracted by the .NET runtime.
- **Privileges/persistence:** manifest is `asInvoker`, `uiAccess=false`. No app
  autostart, service, scheduled task, background persistence or system-setting
  modification was found. UI theme registry changes, local-account creation,
  temporary SMB sharing and USN setup exist in CI helpers, not the shipped app;
  those helpers belong on disposable Windows runners, not a personal workstation.
- **Privacy/network:** hashing reads selected files for the stated scanning
  purpose. Local cache/history contain paths, hashes and metadata and rely on
  profile/filesystem ACLs; they are not encrypted. Explicit Copy Path writes to
  the clipboard; no clipboard read, browser-store access, microphone/camera use,
  application telemetry, HTTP client, listening socket or local API was found.
  User-selected UNC paths can invoke Windows SMB authentication; authorized cloud
  hydration uses the OS/provider and needs real-account privacy validation.
- **Secrets:** source review and targeted GitHub-token/private-key/AWS-key patterns
  found no matches in 123 tracked files or 346 reachable history blobs (none
  skipped by size). This is not exhaustive secret discovery. The Windows account
  test generates a temporary password; release authentication uses `github.token`.
  No application password/token store or credential logging was identified.
- **Web content:** the desktop application is WPF; no Electron, WebView, embedded
  web-content IPC or system-API bridge was found. Opening a document delegates to
  its Windows association after the approved confirmation.

## Verification and limits

Before fixes: portable baseline **67 passed, 26 Windows skips**; acceptance runner
**17 passed**. After fixes: solution Release build, including Windows cross-build,
**0 warnings/errors**; portable baseline **75 passed, 26 skips**; acceptance runner
**17 passed**; release-source tests **8 passed**; targeted Roslyn style verification
(`IDE0005`, `IDE0051`, `IDE0052`, `IDE0059`) passed. These console runners execute
real assertions; `dotnet test` is not a substitute.

Windows runtime confirmation belongs to `windows-11-arm` CI for native ARM64 and
x64 emulation, including WPF confirmation tests, native filesystem/recovery and
standard-account published EXE tests. Linux cross-compilation alone does not
validate Windows behavior. Adversarial staging-namespace/ACL races, native DLL
loading under hostile search paths, malformed SQLite module inputs and signed-in
cloud-provider behavior remain separate isolated-Windows investigations. No real
malicious document, hostile installer or exploit payload was executed. Third-party
native implementations and all possible Windows file associations were not
exhaustively audited. This report does not certify complete application safety.
